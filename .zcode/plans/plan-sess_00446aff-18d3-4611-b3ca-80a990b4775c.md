# 玄穹文枢全链路生产级重构实施计划

## 当前证据与结论

本轮已完成代码级基线审查，并重新执行了当前工作区门禁：

- 后端全量：`637 passed in 72.35s`。
- 前端 `type-check`：通过。
- 前端 Vitest：`45` 个文件通过、`1` 个文件失败；`237 passed / 2 failed`，另有 `1` 个未处理异常。
- 失败集中在 `frontend/src/components/GlobalNavBar.spec.ts`：其 `useLocale` mock 缺少新增的 `pick` 导出，导致任务卡渲染中断；第二个“找不到任务标题”失败是同一渲染异常的连锁结果。
- 因三门禁使用串联命令，Vitest 失败后 `build-only` 未执行，当前不能宣称前端构建通过。
- 工作区已有约 180 个已跟踪文件变更及大量未跟踪成果；实施将全部保留，不重置、不覆盖。

静态审查确认当前已有持久化 TaskRuntime、事件游标、基础 SSE、租约领取、stale 巡检、取消/重试、长篇 checkpoint、TXT 元数据往返等骨架，但仍有发布阻断缺口：

1. TaskRuntime 没有 attempt、lease token、state version；多数终态写、取消、心跳、重试不是数据库 CAS。
2. 普通用户可调用 claim/recover/heartbeat/progress/任意事件接口，甚至伪造终态。
3. 研究、文风、蓝图、导入、章节纲仍以模块级 `_JOBS/_PROJECT_RUNS/_SCHEDULED_RUNS` 参与调度和状态判断。
4. 没有统一持久化 dispatcher；重启巡检主要标 stale/释放章节，不能证明 queued/stale 自动续跑。
5. 蓝图、总纲、章节纲、ChapterBlueprint 没有 revision/If-Match，存在静默覆盖。
6. 定稿没有冻结 selected version/content hash，也没有 FinalizationSession/outbox；重复或并发定稿可重复写快照并覆盖账本。
7. 蓝图和章节纲前端仍使用旧 `run_id` 轮询及时间型假进度；WritingDesk、全局任务卡和旧 SSE 仍是多套投影。
8. 场景资产、版本图和连续性源事件没有完整进入工程导入导出；DOCX 只是阅读版。
9. 当前没有真实浏览器、真实 Provider、真实进程重启、20k 长章、连续十章和 MySQL 并发的完整发布证据。

## 实施原则

- 按批次交付，不尝试一次提交改完 97 个叶子节点。
- 每项 P0 先写可复现失败测试，再修复；随后临时破坏关键判断，确认新增测试失败，恢复实现并重跑门禁。
- 追加式迁移；旧字段和旧 API 保留一个兼容周期，新写入切换到 canonical 模型，不删除旧数据。
- TaskRuntime 只表达执行状态；候选确认、资产确认、定稿状态留在业务资产模型。
- 每批维护机器可读审计台账，记录节点、证据、测试命令、反向验证、产物 hash 和真实验证等级。

## 批次 0：冻结基线并恢复当前门禁

1. 建立审计台账和证据目录，记录当前 commit、完整 `git status`、测试环境版本、OpenAPI/事件/导出样本及本轮 637/637、237/239 结果。
2. 修复 `GlobalNavBar.spec.ts` 的局部 mock，使其包含 `pick`，不改变生产行为；增加断言确保持久化任务卡真实渲染并可取消。
3. 做反向验证：临时移除 mock 中的 `pick`，确认对应定向测试必然失败，然后恢复。
4. 重新执行前端三门禁和后端全量，保存完整输出。同步修正 `backend/pytest.ini` 的测试发现范围，确保 core/db/utils 测试不会被配置语义排除。
5. 不更新任何“最终完成”报告为生产就绪，只在审计台账写当前真实状态。

验收：后端全量通过；前端 type-check、239 项 Vitest、build-only 全通过；反向验证证据可复查。

## 批次 1：TaskRuntime 安全状态机

1. 追加 TaskRuntime 字段与迁移：`attempt`、`lease_generation/token`、`state_version`、`lease_expires_at`、结构化 error、input/config snapshot 引用；事件绑定 attempt，并增加 channel/sequence/segment/hash 字段。
2. 将 claim、heartbeat、progress、cancel、retry、success/failure/cancelled 全部改为数据库 CAS，条件包含旧状态、attempt、lease token 和 state version；queued 取消在单事务内收口。
3. 修正幂等唯一作用域为 owner + task type + scope/input hash，增加 project/chapter 归属校验和 active-task 数据库约束。
4. 封闭 worker 写接口：普通用户仅保留 list/get/events/SSE/cancel/retry；claim/recover/heartbeat/progress/metrics/append-event 改为内部 worker 服务或内部认证入口。
5. 明确 stale 为 attempt 终态；恢复创建新 attempt，不复活旧 attempt。
6. 增加两个独立数据库 session 的并发测试：双 claim、cancel 与 success 竞争、stale 与 heartbeat 竞争、retry 后旧 worker 迟到写、跨 owner 相同幂等键。

验收：旧 worker 无法推进新 attempt；终态无法复活；普通用户无法伪造终态；SQLite 与 MySQL 关键 CAS 测试通过。

## 批次 2：统一 dispatcher 与业务任务迁移

1. 建立 `TaskWorkerAdapter` registry 和持久化 dispatcher；应用启动与周期扫描 queued/recoverable tasks，通过 CAS claim 后分发。
2. 依次迁移 research、style upload/profile、import、blueprint、chapter outline、chapter generation。
3. `_JOBS/_PROJECT_RUNS/_SCHEDULED_RUNS` 降为本进程取消句柄缓存，不再决定任务是否存在、状态、去重或恢复；随后删除状态读路径。
4. 所有任务冻结输入 hash、资产 revision、config snapshot、Prompt revision、预算和 checkpoint/artifact ref。
5. 增加“清空模块级字典、杀进程、双 dispatcher”测试，证明任务可查询、取消、恢复且不重复产物。

验收：无 status API 隐式启动；重启后 queued/stale 自动收敛；双 worker 只能执行一次；各业务状态只从 TaskRuntime 投影。

## 批次 3：统一 SSE 与前端任务投影

1. 后端合并 TaskRuntime SSE、updates SSE 和 writer SSE 的 repository/envelope/cursor/keepalive/终态逻辑，使用 channel 参数过滤。
2. 正文事件补齐 attempt、stream_id、segment_index、sequence、content_hash、is_final；超过 500 条积压可分页连续回放。
3. 前端建立共享 `TaskProjection` reducer，以 task_id + attempt + event_id 幂等，严格区分 content/log/progress/diagnostic/terminal。
4. 将 WritingDesk、GlobalNavBar、管理日志接入同一 reducer；拒绝跨项目、跨 task、旧 attempt 和迟到终态事件。
5. 将蓝图、章节纲、研究、文风、导入从 run_id 轮询迁到 TaskRuntime stream；删除时间型假进度，轮询只作短期兼容降级。
6. 增加真实 HTTP SSE 测试和前端 reducer 测试：断线、Last-Event-ID、重复、乱序、缺口、双客户端、20k 内容三次重连。

验收：前后端正文 checksum 一致；不丢片、不重片；任意页面刷新后可发现并恢复任务；进度只来自服务端事件。

## 批次 4：版本化创作资产与并发编辑

1. 追加 ProjectIntentRevision、LengthContract、BlueprintRevision、BookPlanRevision、VolumePlan、StoryArc、PlotThread、ChapterOutlineRevision、ScenePlanRevision/Scene、ChapterMissionSnapshot。
2. 从现有 JSON/模型生成初始 revision，保留旧字段；新写入只写 canonical revision，同时生成兼容投影并比对 checksum。
3. 所有编辑支持 `base_revision`/`If-Match`，冲突返回 409、当前 revision 和字段级 diff；下游只标 stale，不自动删除。
4. 使用稳定 character/faction/relationship/chapter/scene ID，名称和展示章号不再作为关联键。
5. 统一 BookPlan canonical shape；旧平面结构仅由适配器转换，blocker 不得发布正式资产。
6. 前端补全蓝图、总纲、卷/弧/线程、章节纲富字段和场景编辑器，并显示 revision compare 与下游影响。

验收：后台生成与人工编辑并发时零静默覆盖；富字段往返零丢失；改名/插章/重排不破坏引用；blocker 资产不能进入正文生成。

## 批次 5：正文版本、质量门与长篇恢复

1. 建立不可变 GenerationInputSnapshot，固定 mission/scene/context/research/style/config/prompt/budget revision/hash。
2. 统一续写、整章改写、局部 patch 和候选版本 provenance；新接口只使用稳定 version ID，patch 强校验 base content hash。
3. 章节版本增加 parent/base version、content hash、operation、author/provider、created/finalized 时间；禁止整体替换或静默淘汰被引用历史。
4. 长章正文移出任务 payload，使用 segment artifact/checkpoint；完成段以 attempt + segment + hash 幂等。
5. 统一质量门 DTO：blocker/warning/degraded；统一小说字数口径；污染候选隔离，硬事实、世界规则、时序和重大伏笔 blocker 不可绕过。
6. 建立题材分层人工标注集，分离硬结构门和软审美评分。

验收：20k 章节断线/取消/进程重启不重段、不跳段、不串段；正式正文零协议污染；旧评审随内容 hash 变化自动 stale。

## 批次 6：原子定稿与连续性账本

1. 增加 FinalizationSession、commit_id 和 DomainEventOutbox；定稿开始时冻结 selected version/content hash/context revision。
2. 正文选中、章节业务状态、快照、硬事实事件、人物/势力状态、时间线、因果、伏笔和线索使用同一 commit_id。
3. 数据库内状态在一个事务中提交；向量、研究索引等外部副作用由 outbox 幂等执行并可重试。
4. 硬事实、append-only domain event 与 LLM 摘要分层；摘要不得覆盖硬事实。线索、伏笔、图谱等成为单一源事件的派生投影。
5. 重复定稿使用幂等键；正文版本变化时旧会话返回 409；失败显示 finalizing/ledger_syncing/failed，不伪装 finalized。
6. 对每个定稿步骤做故障注入，并测试版本变化、重复定稿、两个并发定稿、投影重建和正文回退。

验收：无半定稿、无重复副作用、无账本丢更新；正文回退后派生投影可重建且与选中版本一致。

## 批次 7：Provider、研究、文风与成本治理

1. 实现 ConfigSnapshot、PromptRevision、RetryBudget、TimeoutPolicy 和用户/Provider/模型共享并发限流。
2. 每次调用记录预留/实际 token 与费用，内部/外部重试共用一个预算；超预算暂停等待确认。
3. 研究资料版本化并绑定来源 URL、抓取时间、片段、可信度和上下文快照。
4. StyleProfileRevision 绑定来源、置信度、授权/版权限制及项目；上传统一格式矩阵、大小、恶意文件和保留期限治理。
5. 建立敏感字段 registry，正文和大 payload artifact 化，执行密钥/隐私 canary 扫描。

验收：同 attempt 配置不漂移；调用数不超预算；双项目不串研究/文风；日志和任务 payload 无密钥泄漏。

## 批次 8：完整工程导入导出

1. 定义版本化工程 manifest、资产清单、checksums、ID 映射和兼容迁移器。
2. 纳入所有 revision、scene assets、version graph、selected relation、评审/patch provenance、连续性源事件、研究和文风引用。
3. 区分 TXT/DOCX/EPUB 阅读版与完整工程包；DOCX 不再宣称可完整往返。
4. 导入使用 staging project、业务幂等键和两阶段发布；损坏、取消或重启不得留下正式项目残片。
5. 空库导入后重建派生投影，逐项核对资产数量、关系和 checksum。

验收：完整工程 roundtrip 图同构、hash 匹配；损坏输入零正式残留；重复提交只发布一次。

## 批次 9：真实生产验收与发布门禁

1. 引入 Playwright 真实浏览器流程及 axe、窄屏、键盘、长文性能测试。
2. 使用真实 Provider 执行短章串行十次、真实入口连续生成并定稿 1—10 章。
3. 真实 20k 章执行断线、取消、进程 kill 和续接。
4. 双用户、双项目、双 worker 执行一成一败、一取消一成功及跨项目隔离。
5. fresh/legacy Alembic 000→最新，SQLite/MySQL 两套关键事务与并发测试。
6. CI 改为执行正式后端全量、前端三门禁、迁移、浏览器核心流程和证据归档；任何发布阻断项出现立即失败。

只有上述真实门禁连续两轮通过，才将能力从 `IMPLEMENTED_UNVERIFIED/TESTED` 提升为 `REAL_VERIFIED`，并允许声明生产级。
