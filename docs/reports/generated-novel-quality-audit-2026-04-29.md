## 4. 缺陷判定（按视角）

### 代码编写者视角
- 历史生成任务存在 `generating` 残留，说明此前长任务缺少可靠的超时恢复、可观测状态与后台化队列闭环。
- 数据库中项目、蓝图、大纲、章节、版本之间存在部分断链/缺失，需要在服务层增加一致性检查与修复入口。
- 输出 JSON 只记录轮询快照，缺少最终章节正文、失败分类和可复现实验参数，不利于回归定位。

### 作家视角
- 部分项目只有灵感/蓝图或大纲，没有完成章节，写作流程容易在“大纲已生成→正文未落地”之间中断。
- 失败章节的摘要多为系统故障提示，不是可继续创作的文学性摘要，恢复体验会破坏创作连续性。
- 短正文版本与字数统计偏差会让作者误判章节完成度。

### 读者视角
- 已有成功正文整体可读，但项目间完成度差异很大；读者会遇到章节缺失、连载断裂或正文长度不稳定。
- 若 UI 未显式标注生成失败/生成中残留，读者会以为小说内容缺章或质量失控。

### 项目开发审批者视角
- 核心风险不在单点 UI，而是端到端生成链路的完成率、恢复率、审计证据和自动化验收不足。
- 当前已补入后台化、超时与 smoke 验证，但还应继续补数据库一致性修复工具和更完整的 E2E 生成验收。

## 5. 下一步优化步骤

4. 为灵感模式→蓝图→大纲→章节生成新增完整 E2E smoke：SQLite 隔离库、低字数 mock/真实兼容路径、截图和 JSON 报告。
5. 输出 JSON 增加最终正文摘要、选中版本、错误分类、模型参数和重试建议，形成可审计产物。
