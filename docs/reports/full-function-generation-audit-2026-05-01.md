## 二、重点链路：灵感模式到大纲

1. 前端 `/inspiration` 创建或恢复项目。
2. 用户输入灵感，调用 `/api/novels/{id}/concept/converse`。
3. 后端读取 `concept` prompt，经 LLM 返回结构化对话控制。
4. AI 判断 `is_complete` / `ready_for_blueprint`。
5. 前端进入蓝图确认。
6. 后端蓝图任务通过 `/blueprint/generate/start`、`/status`、`/cancel` 运行。
7. 蓝图由 `screenwriting` prompt 生成，并写入项目蓝图与章节大纲。
8. 前端确认保存后进入写作台。

主要风险：蓝图同步旧路径仍存在；取消不能真正中断已进入的 LLM 调用；任务状态以内存 job 为主，重启恢复有限。

## 三、重点链路：小说生成

1. 写作台选择章节。
2. 生成章节调用 writer 路由。
3. 后端构建上下文、调用流水线、生成候选版本。
4. 前端轮询章节状态。
5. 版本区展示候选版本。
6. 可评估、比较 Diff、选择最终版本。
7. 健康检查展示正文风险。
8. 后端导出要求章节 successful 且 selected_version 非空。

主要风险：章节任务依赖 BackgroundTasks；版本操作仍有 index 约定风险；手工编辑默认覆盖选中版本，历史回溯不足。

## 四、已生成小说反映出的生成能力

现有报告显示：项目约 40 个、章节大纲 254 条、章节记录 35 条、正文版本 68 个。系统能完成长篇规划、多版本生成、导出阻断治理。

能力优点：
- 氛围塑造较强。
- 类型感明确。
- 可生成较长章节。
- 有多版本和评估意识。
- 已有健康检查和导出保护。

能力短板：
- 大纲数量远高于正文数量，长链路完成率不足。
- 历史元数据和正文仍有污染记录。
- 短正文/占位正文曾进入版本系统。
- 正文偏氛围堆叠，事件推进密度不足。
- 重复意象控制不足。
- 审计偏工程结构，文学质量维度不足。

## 五、四视角缺陷

### 代码编写者视角
- 视觉系统混用：Material、XQ、Tailwind、Naive UI、本地补丁并存。
- 任务状态分散，状态机没有集中表。
- API 错误处理重复。
- 后台任务非持久化。
- 版本 index 操作存在错位风险。

### 作家视角
- 灵感到蓝图有价值，但蓝图生成过程透明度不足。
- 章节生成缺少“本章目标/冲突/伏笔/钩子”的强约束。
- 生成文本容易重氛围轻推进。
- 文风中心入口存在，但学习结果与章节生成的因果关系展示不足。

### 读者视角
- 成熟样本有氛围和类型感。
- 部分内容会重复意象，节奏偏慢。
- 英文夹杂、历史乱码会破坏沉浸。
- 章节完整性和钩子稳定性需要更强门禁。

### 项目开发审批者视角
- 功能面广，但关键路径仍依赖非持久后台任务。
- 默认管理员上下文存在部署安全风险。
- 前端导出入口/导出预检仍需产品化。
- 自动化测试已有基础，但文学质量审计还不够。
- UI 视觉已经在本轮收敛，但仍需结构级替换旧系统。

## 六、简洁优化步骤

1. 统一视觉系统：以冷色 XQ token 为唯一主视觉，旧 md/本地按钮逐步迁移。
2. 统一蓝图生成路径：全部走后台 start/status/cancel。
3. 持久化章节生成任务：用 DB job 或队列替代纯 BackgroundTasks。
4. 版本操作改用 version_id，index 只展示。
5. 新增文学质量只读审计，不改历史小说。
6. 新生成正文入库前加质量门禁。
7. 前端补导出预检和导出入口。
8. 将状态机集中化。

## 七、详细优化方案

### P0
- 统一灵感蓝图异步任务路径。
- 导出前健康检查产品化。
- 新生成版本入库门禁：长度、乱码、占位符、错误提示、selected_version 有效性。

### P1
- 章节任务持久化。
- version_id 替代 version_index。
- 手工编辑创建新版本而不是覆盖旧版本。
- 新增 `tools/audit_literary_quality.py` 只读文学审计。

### P2
- 章节目标检查器：事件、人物选择、冲突升级、伏笔、结尾钩子。
- 重复意象降频表。
- 文风应用透明化：展示当前章节用了哪些风格规则。

### P3
- 拆分 `main.css`：base、visual constitution、legacy overrides。
- 组件化后台、设置、风格中心、写作桌面旧结构。
- 增加 E2E 色相、按钮风格数量、关键入口可见性检测。
